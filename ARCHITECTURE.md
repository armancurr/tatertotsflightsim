# Tater's Flight Sim — Architecture

This document explains how Tater's Flight Sim is built, in plain English. It is written for a
developer (or an AI agent) who has never seen the code. Read `ELEVATOR_PITCH.md` first for *what*
the project is; this file is *how* it works. `REPO_MAP.md` lists every file; `RESUME.md` says where
the work stopped.

---

## 1. The big picture

The simulator is a single web page (`index.html`) that loads one TypeScript entry file
(`src/main.ts`). It first checks for WebGL 2 and picks a quality preset (`src/boot.ts`,
`src/render/capabilities.ts`, `src/render/quality.ts`), then loads the game itself as a separate
chunk (`src/game/app.ts`); anything that goes wrong ends on a friendly error card, not a blank
page. There is no server logic — Vite serves the files during development, and the
build is a folder of static files. Everything — terrain, trees, buildings, sky, clouds, the
aircraft, textures, sounds — is **generated by code** at start-up or on the fly. Nothing is
downloaded at runtime, so there is nothing that can fail to load.

The code is split into two kinds of modules:

| Kind | What it means | Examples |
| --- | --- | --- |
| **Pure simulation** | Plain TypeScript maths. No three.js, no DOM, no clock. Same input → same output, every time. This is what the tests hammer. | `src/physics`, `src/input/controlSystem.ts`, `src/camera/cameraRig.ts`, `src/game/loop.ts`, `src/ui/instruments.ts`, `src/world/heightfield.ts`, `src/world/layout.ts` |
| **Presentation** | Draws or plays what the simulation says. Uses three.js (WebGL2), the DOM, Web Audio. Never changes the simulation state. | `src/render`, `src/aircraft`, `src/world/terrain`, `src/ui/hud.ts`, `src/audio`, `src/fx` |

This split is the single most important design rule: **the renderer only draws what the physics
says.** It is why the flight model can be tested to the decimal place without a browser.

```
 keyboard / mouse / gamepad
          │
          ▼
  input (pure) ── smoothed Controls ──▶ physics.step()  ×120 per second (fixed step)
                                              │
                                              ▼
                                        AircraftState ──▶ window.sim (for tools & tests)
                                              │
                   interpolate between the last two physics states (smooth at any frame rate)
                                              │
        ┌──────────────┬──────────────┬───────┴───────┬───────────────┬───────────────┐
        ▼              ▼              ▼               ▼               ▼               ▼
   aircraft model   camera rig    instruments      sky & sun      world systems     audio
   (surfaces, gear, (4 views,     (needles, VSI    (fog, clouds,  (terrain, water,  (engine,
    prop, lights)    transitions)   lag, warnings)  shadows)       trees, towns…)    wind, horn)
        └──────────────┴──────────────┴───────────────┴───────────────┴───────────────┘
                                              │
                                              ▼
                                   renderer.render(scene, camera)
```

## 2. Coordinates and units (read before touching any maths)

- **World:** metres. `+X` = east, `+Y` = up, `+Z` = **south** (so north is `−Z`). `y` is height
  above mean sea level. This is the three.js convention, so the renderer needs no conversion.
- **Heading:** degrees clockwise from north (0 = north/−Z, 90 = east/+X).
- **Aircraft body:** the same as a three.js object: `+X` right wing, `+Y` up, **`−Z` the nose**.
  The origin is the centre of gravity. The physics' orientation quaternion can be copied straight
  onto the 3D model.
- **Aircraft-convention quantities** (angle of attack α, sideslip β, roll/pitch/yaw rates p/q/r,
  roll/pitch/yaw moments L/M/N) are converted **only** through the helpers in
  `src/physics/frames.ts`. Never re-derive signs by hand — `tests/physics/frames.test.ts` pins them.
- Units are SI inside the code. Knots, feet and feet-per-minute appear only at the edges (HUD,
  `window.sim`, config keys whose names end in `Kt`, `Ft`, `Fpm`, `Deg`).

`src/types.ts` holds these conventions in its header and defines the shared shapes
(`AircraftState`, `Controls`, `Environment`, `InstrumentReadings`, `SimSnapshot`).

## 3. One config file

`src/config.ts` holds **every tunable number**: the aircraft (mass, wing area, lift/drag
coefficients, stall angle, stability derivatives, engine power, gear geometry, landing limits),
controls (key bindings, smoothing rates), cameras (distances, FOVs, transition time), the world
(seed, airport, terrain LOD, trees, towns, water, traffic), the atmosphere (sun presets, fog,
exposure, clouds, shadows), rendering quality, audio and HUD. Each top-level section is owned by
one module. Balancing the sim is one edit; tests can clone the config (`cloneConfig()`) and change
values without touching the real one.

## 4. The frame (src/game/app.ts)

`startApp()` builds everything once, then runs this every animation frame:

1. **Input** — `input.frame()` collects held keys, key presses, mouse drags/wheel and gamepad
   axes; `updateControls()` turns them into smooth control positions (throttle, yoke, rudder, trim,
   flaps notch, gear handle, brakes, engine switch) plus discrete **actions** (reset, pause,
   camera change, help, mute, time of day).
2. **Physics at a fixed 120 Hz** — `FixedStepLoop.advance()` runs `step(state, controls, 1/120,
   env)` as many times as real time requires (capped so a slow frame can't spiral). The render
   frame rate never changes the physics.
3. **Interpolation** — the aircraft is drawn between the last two physics states, so motion is
   smooth at 60, 90 or 144 Hz.
4. **Instruments & aircraft animation** — readings (with real-instrument lag) drive the HUD and the
   cockpit panel; control positions drive the elevator, ailerons, rudder, flaps, gear and prop.
5. **Camera** — the camera rig computes the pose for the current view and blends between views.
6. **World** — the atmosphere updates (sun shadows follow the aircraft, clouds, fog), then every
   **system** updates (terrain tiles, trees, towns, water, traffic, effects, audio, HUD).
7. **Render**, then update `window.sim` and the FPS meter.

While paused, the world keeps rendering (so it streams in), but the physics and the control
toggles freeze.

## 5. The physics (src/physics)

A six-degrees-of-freedom rigid-body model, deterministic and pure, shared by every aircraft: the
config passed to `step(state, controls, dt, env, cfg)` selects the airframe, the engine type
(`engine.type`: `'piston'` → `engine.ts`, `'jet'` → `jet.ts`, a turbofan with optional
afterburner, spool lag, thrust lapse and ram recovery) and fly-by-wire (`fbw`: `fbw.ts`, the
F-16's g / roll-rate command with an angle-of-attack limiter). Jets add transonic and supersonic
drag (`aero.transonic`), and the gun's recoil (`recoil.ts`) pushes back while the trigger is
held. `step()` returns a **new** state (it never mutates its input). The description below is the
Cessna's; the F-16, A-10 and 747 use the same machinery with their own numbers.

- **Air data:** the aircraft's velocity relative to the air (minus wind) is rotated into the body
  frame to get airspeed, angle of attack and sideslip; air density follows the standard atmosphere.
- **Aerodynamics (`aero.ts`):** the lift coefficient rises with angle of attack and flaps, rounds
  off at the stall angle (≈15.5° clean) and collapses toward flat-plate behaviour past it; drag is
  parasite + gear + flaps + induced (lift²) + sideslip, rising to flat-plate drag past the stall.
  Pitch, roll and yaw moments use published C172 stability derivatives (damping, dihedral effect,
  weathercock stability, adverse yaw). The propeller slipstream adds airflow over the tail (so
  elevator and rudder work at full power on the ground). Past the stall the wing loses its roll
  damping — an uncoordinated stall drops a wing. **Ground effect:** near the runway the wing makes a
  little more lift and less induced drag (McCormick's formula).
- **Engine (`engine.ts`):** power follows the throttle with a lag, falls with air density; thrust
  comes from power and airspeed (strong at low speed, falling as speed rises); a windmilling prop
  adds drag. The engine can be switched off, cranks for ~1.4 s to restart, and fails in a crash.
- **Ground (`ground.ts`):** three spring-damper struts (nose and two mains) at the exact wheel
  positions of the 3D model, rolling friction by surface (runway, grass, dirt…), brakes, sideways
  tyre grip, nosewheel steering from the rudder. Structural points (prop tip, wingtips, tail,
  belly…) that touch the ground mean a crash; a gentle tail scrape only skids.
- **Systems:** flaps move at the electric motor's rate; the gear takes 5 s and only retracts after
  1.5 s of continuous flight (squat-switch interlock).
- **Flight phases:** `ground` → `airborne` → (touchdown) `landed` or `crashed`; a `stalled` flag
  while airborne. Touchdowns are rated by vertical speed (butter < 120 fpm, smooth, firm, hard; over
  900 fpm the gear collapses). Crashes record a reason, the speed and position; the engine fails
  and the state freezes until reset. Over-G (6.5 g) or diving past 1.3 × Vne breaks the airframe.
- **Trim solver (`trim.ts`):** finds the throttle, pitch and trim for a steady flight condition —
  used for the final-approach reset (Shift+R) and teleports.

Calibration results against the pilot's handbook are in the comment block at the top of
`src/physics/aircraft.ts`.

### 5b. Helicopters (`rotor.ts`)

An aircraft whose config has a `rotorcraft` section (the Bell 206B-3 JetRanger) goes through the
same `step()` — air data, ground contacts, flight phases, crash rules and the rigid-body
integration are shared — but `rotor.ts` replaces the wing (`aero.ts`) and the engine:

- **Main rotor:** blade-element thrust with linear twist and uniform inflow, referenced to the
  tip-path plane; the induced velocity is a state (Pitt–Peters dynamic inflow) relaxing toward
  momentum theory (Glauert), blended at low in-plane speed with an empirical curve through the
  **vortex-ring state** (thrust loss and buffet in slow, steep descents). **Ground effect**
  (Hayden's fit to flight data) and **translational lift** fall out of the inflow. The disc's tilt
  (quasi-steady teetering flapping) is the cyclic plus blowback, the lateral flapping from coning
  and the transverse-flow inflow gradient, and the lag and cross-coupling from the body rates; a
  teetering rotor has no hub moment, so control power fades with thrust (low g). Past a CT/σ that
  falls with speed the retreating blade stalls (pitch-up, roll left, drag). Torque = CT·λ + profile
  (with an induced-power factor κ = 1.15).
- **Tail rotor:** the same thrust/inflow/VRS model on the pedals, gear-driven; its power loads the
  drivetrain.
- **Airframe:** fuselage drag (front/side/top areas) in the rotor wash (hover download), unstable
  fuselage pitch/yaw moments, a stabiliser that meets the rotor wake below ~25 kt and a cambered
  fin that unloads the tail rotor in cruise.
- **Drivetrain and turboshaft:** rotor speed is a state (`I·dΩ/dt = Qshaft − Qrotor`); the fuselage
  reacts the shaft torque (the nose yaws right with power; left pedal to hover). An N2 governor
  (P + I + collective anticipator) commands the Allison 250's power through a gas-generator lag,
  limited by density; it can over-torque, and it caps the torque while running the rotor up on
  the ground. A **freewheel** lets the rotor overrun the engine: shut it down (E) and the rotor
  autorotates, its speed set by the collective.
- **Skids (`ground.ts`):** four spring-damper contacts with stick-slip (anchored) friction, so a
  parked helicopter doesn't creep under rotor torque and a skid pinned while sliding sideways rolls
  it over (**dynamic roll-over** → "Main rotor strike"). Rotor tips and the tail rotor are
  structural points; negative g past −0.5 is mast bumping.
- **Stability assist (`stabilityAssist` in `rotor.ts`, K):** between the pilot and the blades —
  attitude command / attitude hold on the cyclic, heading hold (hover) or sideslip-nulling turn
  coordination (forward flight) on the pedals, and a position hold in the hover with the stick
  centred. It engages as the skids get light (half the weight on the rotor). Off, the controls drive the blades directly.
- **Trim (`solveRotorTrim`):** Newton on all six force/moment balances (collective, cyclic, pedals,
  pitch, bank), marching up from the hover; used by Shift+R and teleports (speed 0 = a hover).

`Controls.throttle` is the collective; `AircraftState.rotor` carries the rotor, engine and assist
state (the HUD, the audio, the model and `window.sim.rotor` read it).

### 5c. Boats and ships (`hull.ts`)

A config with a `watercraft` section (every vessel) is handed whole to `stepVessel()` in
`hull.ts`: a vessel has no wing, gear or runway, and its phase is `'afloat'` (or `'crashed'`). One
model covers every size — a battleship would be a different station table and different numbers:

- **The hull is a table of stations** (`hull.stations`: keel, chine, deck edge; bow → stern) that
  the physics resamples into a grid of vertical **columns** and the 3D model lofts
  (`src/vessels/hullLoft.ts`) — what floats is what you see.
- **Buoyancy:** each column's wet part displaces water (ρ g V at its centroid) against the **same
  Gerstner sea the renderer draws** (`src/world/water/waves.ts`, with the shader's shoaling),
  sampled on a coarse grid over the hull at the vessel's wave clock. Heave, pitch, roll, righting
  moment and riding the waves come from the shape. Columns also feel linear + quadratic vertical
  damping relative to the moving surface.
- **The hull's own wave:** a Kelvin transverse wave (λ = 2πU²/g, crest at the bow, zero mean) added
  to the surface the columns see: near Fn 0.5 its trough sits under the stern — the hump trim of a
  planing hull, the sinkage and trim of a ship.
- **Planing (Savitsky):** dynamic lift ½ρV²B²C_Lβ from the running trim (flow angle + the wet
  bottom's rocker) and the wetted length/beam, at Savitsky's centre of pressure, laterally at the
  wet bottom's immersion centroid shifted toward the side leading into a skid (so a V-bottom banks
  into its turns), with the pitch damping of the lift spread along the bottom. At planing speed
  most of the hydrostatic pressure turns into this lift (the transom runs dry).
- **Resistance:** ITTC-57 friction × form factor on the live wetted surface; a residuary Cr(Fn)
  table (the hump); windage. **Manoeuvring:** Clarke's linear derivatives from the live length,
  draft, beam and block coefficient, strip cross-flow drag, added mass by immersion.
- **Propulsion:** per propulsor, a governed marine diesel (torque rise, turbo lag) on a shaft whose
  speed comes from the torque balance with a propeller's KT(J)/KQ(J) curves; pods turn the thrust
  line, shaft drives have a rudder in the slipstream; the leg or rudder is also a foil. Trim tabs,
  a helm lever through neutral into astern, mooring lines at the berth.
- **Contacts:** points round the hull against the sea bed and the shore (`groundHeight`) and
  structures (`obstacleTop`: the marina's pontoons, quays and moored boats); a hard or fast hit
  holes the hull; lying past 75° capsizes it.

The **sea clock** is shared: the vessel carries `vessel.seaTime` and the app hands it to every
system as `SystemFrame.waveTime`, so the water is drawn at exactly the time the hull floats on (the
sea pauses with the sim while a vessel is driven).

Four vessels use it: the Princess V50 (planing, IPS pods), the Sea-Doo RXP-X 325 (a `'jet'`
propulsor — pump flow, steerable nozzle, iBR bucket — on strip-theory planing, with a rider who
leans and rights a capsize), the MS Tater Star (displacement, two shafts and rudders, six `'thruster'`
tunnel thrusters on the aileron axis) and the USS Iowa (four shafts, twin rudders). An at-speed
start (`createVesselState` with `speedKt`) pre-runs the hull in calm water, holding the speed and
the shafts at the lever's rpm while the helmsman trims the lever on the surge acceleration, so a
jet ski and a battleship both start in gear at the speed asked for.

**The port** (`src/world/port.ts`, structures in `src/world/harbour/`): three berths chosen by
vessel (`vesselBerth(def)`: the marina's visitors' pontoon, the cruise terminal east of it, the
naval pier west of it — piers on piles built out to deep enough water), an open-sea start, the
Gull Island lighthouse, the marina's harbour lights and IALA-A channel buoys. The berthed-ships
system shows the cruise ship and the Iowa at their berths when you aren't driving them. Pier decks
and a berthed ship's deck are **landable decks** (`Environment.deckTop`, `registerDeckSource`):
aircraft stand on them and measure AGL from them (the helicopter lands on the Iowa's helipad or the
oil rig's helideck); vessels ignore decks and hit the obstacle. **Soft obstacles**
(`softObstacleTop`: the race buoys) push a hull away without damage. `R` goes back to the berth,
`Shift+R` starts underway offshore.

**Offshore and wildlife** (`src/world/offshore/`, `src/world/wildlife/`, docs/OFFSHORE.md): the
Tater Alpha platform with its helideck and flare, a 16-turbine wind farm yawing with the wind, the
jet-ski race course with a lap timer (`src/ui/raceHud.ts`), and dolphins (pods that come and ride
a moving bow), humpbacks (blows, fluke dives, breaches), gulls and seals — instanced, animated in
the vertex shader, a handful of draw calls.

**The wake** (`src/game/systems/playerWake.ts`, `src/world/water/wake*.ts`) is part of the sea
surface: the player's hull renders a Kelvin wave field plus a foam-density and track-direction map
that the sea shader samples — marbled propwash that ages into lace, aerated turquoise water, the
centreline slick, whitecaps on the steep wake crests — scaled from the hull's length, beam, speed and
engine load, from a jet ski's rooster tail to a battleship's kilometre-long lane.

## 6. Controls, cameras and the loop

- **Controls (`src/input`)** — pure `updateControls(state, inputFrame, dt)`. Keys move the yoke
  toward full deflection at a set rate and back to centre when released (the elevator eases off
  slowly, like a pilot relaxing back pressure); throttle and trim stay where you leave them; flaps
  step through 0/10/20/30°; G toggles the gear handle. Mouse-yoke (Y) and gamepads are supported.
  The DOM adapters stop bound keys scrolling the page and clear held keys when the window loses
  focus (no stuck keys).
- **Cameras (`src/camera`)** — pure `updateCameraRig()`: **cockpit** (pilot's eye, head look with
  the mouse), **chase** (spring-damped behind the aircraft), **external** (a fly-by spotter that
  re-positions ahead of the aircraft), **orbit** (drag to rotate, wheel to zoom, slow auto-spin).
  Switching views blends position, rotation and field of view over ~0.9 s. Cameras never go below
  the ground. Camera shake comes from the ground roll, stall buffet and crashes.
- **Loop (`src/game/loop.ts`, `fps.ts`, `interpolate.ts`)** — the fixed-step accumulator, the FPS
  meter (1-second fps, session average, worst second, 1 % low, long frames), and pose interpolation.

## 7. The world

### 7.1 Geography as data (pure)
- `layout.ts` — the whole map as plain data from the config and a seed: the airport (runway 36/18,
  taxiways, apron, building spots), the coastline and bay with islands, two lakes, the river from
  the mountains to the sea, 26 towns (a coastal city, a town, villages, hamlets), and the road
  network.
- `heightfield.ts` — `terrainHeight(x, z)`: rolling farmland, a mountain range to the north,
  carved river and lake beds, beaches into the sea, and the airport plateau **exactly** flat at
  30 m. `landcover.ts` decides what covers the ground (forest, field, grass, rock, snow, sand,
  town, water) and `treeDensity()`; `fields.ts` is the farm-field pattern, shared bit-for-bit with
  the terrain shader.
- `environment.ts` — the physics' view of the world (`Environment`): ground height and slope,
  surface type, water level, and **obstacles** (trees, buildings, the tower register themselves),
  built from the same functions the renderer draws — **what you see is what you hit**.
- `runway.ts` — runway coordinates shared by the physics (spawn, landing rating) and the world:
  `runwayFrames()` for both runways, `runwayEnds()` / `runwayEndFrame()` for the four ends
  (`?rwy=`), `runwayAt()`, `runwayCrossing()`.

### 7.2 Drawing the world
Heavy generation (terrain tiles, tree chunks, building placement, road meshes, detail textures,
water depth maps) runs in **Web Workers**; the main thread only uploads results a few per frame, so
flying fast never hitches.

- **Terrain (`src/world/terrain`)** — a quadtree of tiles around the camera: small detailed tiles
  near, big coarse ones far, out to ~60 km, with skirts to hide cracks, pooled geometry and correct
  bounding spheres for culling. Heights **and colours** morph between detail levels so nothing
  pops. The shader (built on three.js's standard material, so lighting, shadows and fog work)
  paints the ground from the landcover: realistic farmland (ten crop types, drill rows, tractor
  tramlines, ploughed furrows, hedges and farm tracks, soil patterns), forest floors, town lots
  with lawns and driveways, rock with warped strata and scree, snow that lingers in gullies,
  beaches. Close up, eight **procedurally generated detail textures** (grass, crop, soil, gravel,
  rock, sand, snow, straw) are blended by height, with random per-tile offsets so nothing repeats.
- **Water (`src/world/water`)** — twelve wind-driven wave trains (the same maths is exposed as
  `waterSurfaceAt()` for boats), an FFT-generated ripple texture for sparkle and the sun's glitter
  path, a depth/shore map baked in a worker around the camera (turquoise shallows over sand, dark
  deep water, surf lines and foam), a continuous flowing river ribbon that coarse terrain can never
  hide (a natural cross-section with gravel and sand bars, visible current, patches of whitewater
  and boulders), rivers and lakes that reflect the land around them, reeds swaying on lowland
  banks, and calm mirror-like lakes on still mornings.
- **Airport (`src/world/airport`)** — two runways: 36/18 and **03/21** crossing it at 30° in its
  northern half (`CONFIG.world.airport.runways`; `runway.ts` `runwayFrames()` / `runwayEndFrame()`;
  `?rwy=03` starts on any runway end). Pavement pieces are cut so no two surfaces overlap (36/18
  owns the intersection, 03/21 owns its taxiway crossings), with aggregate, rubber marks, cracks
  and patches, worn FAA paint (03/21's interrupted inside 36/18, hold positions on it and on the
  taxiways that cross it), the control tower, hangars (a maintenance hangar with its doors open),
  T-hangar rows, an ARFF station, a flight school, the FBO, a fuel farm, VOR/DME, the ILS localizer
  and glideslope for 36, windsocks at every runway end, a perimeter road and fence with gates,
  ~26 parked Cessnas and Pipers, King Airs, a helicopter on its pad, ARFF trucks, refuelers, a
  patrolling ops pickup, cars, signs, and ~400 lights in one draw call: edge, threshold, REILs,
  taxiway, MALSR with the sequenced "rabbit", the rotating beacon and four working **PAPIs**.
  `field.ts` is the pure layout of everything beyond `layout.ts` (landcover reads its pavement
  for the physics' surface types); buildings, aircraft and vehicles are obstacles.
- **Roads (`src/world/roads`)** — a junction network (2,000+ nodes) turned into road surfaces with
  sidewalks, shoulders and soft verges, US-style markings (double yellow, dashed lines, crosswalks,
  stop bars), dirt farm tracks, bridges with decks, piers and guard rails, and ~4,000 street lights
  that glow at dusk. A small depth pull keeps roads from sinking into coarse terrain.
- **Towns (`src/world/towns`)** — ~11,000 buildings and ~19,000 garden and street trees in 26
  towns: houses with gable/hip roofs, chimneys and dormers, detached garages and swimming pools,
  terraces, apartment blocks, shops with awnings, glass towers (some round), churches, town halls,
  schools, water towers and storage tanks, industrial sheds, farmsteads with barns and silos. One
  small mesh per building type is stretched per instance in the vertex shader;
  a facade shader draws windows, doors, shopfronts and roof materials; windows light up at dusk.
  Placement runs in a worker; far towns collapse into one self-culling mesh. Rooftops are obstacles.
- **Trees (`src/world/vegetation`) and grass (`src/world/grass`)** — seven species built from leaf
  cards (spruce, pine, broadleaf, birch, poplar, willow, bush) with back-lit leaves and wind sway;
  multi-angle **impostors** (pre-rendered images) take over beyond ~210 m and fade out around
  4.5 km. Forests, clearings, hedgerows on field edges, orchards, willows along the river. Grass
  tufts and wildflowers appear near the camera when flying low. Trees are obstacles — flying into a
  forest is a crash.
- **Traffic (`src/world/traffic`)** — ships and boats (`sea.ts`: the Port Chateau marina with
  its moored boats, sailing yachts that tack and gybe with the wind, motor yachts, trawlers, a
  harbour launch, a bay ferry, a container ship, a tanker and lake boats, with Kelvin wakes and
  wave-driven heave, pitch and roll) and air traffic (`air.ts`: runway-36 circuits, crossing light
  aircraft, a helicopter over Port Chateau, airliners with contrails). Both are pure functions of a
  traffic clock (`?tt=` sets it), drawn in a handful of batched draw calls by the `ships` and
  `airTraffic` systems. See [docs/ADDING_BOATS.md](docs/ADDING_BOATS.md).
- **Cars (`src/world/cars`)** — road traffic on the lane graph built from the road network: an
  intelligent-driver model (`idm.ts`) with junction holds, nine vehicle types from hatchbacks to
  semis, buses and farm tractors (`specs.ts`), parked cars at the kerb and in car parks, head- and
  tail-lights at dusk, and far-away cars as cheap shapes. See
  [docs/ADDING_VEHICLES_AND_TARGETS.md](docs/ADDING_VEHICLES_AND_TARGETS.md).

## 8. Sky, light and rendering (src/render)

- **Renderer (`renderer.ts`)** — WebGL2 with a **reversed float depth buffer** (no flickering
  between the 8 cm cockpit panel and a mountain 60 km away; browsers without `EXT_clip_control`,
  such as Firefox and Safari, fall back to a logarithmic depth patch in `logDepthPatch.ts`),
  rendering in linear HDR with up to 4× MSAA, then one output pass with a filmic tone map.
  **Quality presets** (`quality.ts`, `?quality=auto|low|medium|high`): `auto` starts at a
  conservative resolution and dynamic resolution (`dynamicResolution.ts`) climbs when the frame
  rate has headroom and drops when it hasn't. Below 85 % of the resolution cap, `auto` and `medium`
  step MSAA down (4 → 2 → 0) before lowering the resolution further, and restore it when the frame
  rate recovers; `high` keeps 4×. `?dyn=0&msaa=N` pins both for A/B measurements. Software renderers
  and older integrated GPUs start lower. A lost WebGL context shows a banner and a Reload button.
- **Camera look (`atmosphereState.ts`, `post.ts`, `bloom.ts`, `metering.ts`, `toneMapping.ts`)** — the
  camera meters the light like a real one: a time-of-day exposure from the ground illuminance (partial
  adaptation: golden hour +1.2 EV, dawn +1.9 EV over morning's 2.2), a partial auto white balance with a
  golden-hour warm / blue-hour cool tint, and a GPU eye adaptation (centre-weighted log-average of the
  frame, ±0.5 EV, eased, no readback). HDR highlights bloom through a ½-res dual-filter chain (off on
  `?quality=low`), and the filmic curve keeps gradation in clouds and white paint. `?ae=0` / `?meter=0`
  switch the camera automation off for A/B comparisons.
- **Atmosphere (`atmosphere.ts`)** — a physically based sky (single scattering: deep blue overhead,
  pale haze at the horizon, a real sun disc), a sun light whose colour follows its height, soft
  shadows that follow the aircraft, and a sky environment map for reflections. Four time-of-day
  presets (N key).
- **Aerial perspective (`fog.ts`)** — three.js's fog code is replaced for **every** material:
  height-based haze that is blue away from the sun and warm toward it, matched to the sky at the
  horizon, so distant hills fade like real ones. Any material with `fog: true` gets it for free.
- **Clouds** — by default a **volumetric** ray-marched cumulus layer (reduced resolution,
  temporal accumulation, depth-aware compositing, lit from the sun, drifting with the wind), with a
  GPU-time budget controller that degrades it or falls back to instanced billboard clouds when the
  frame is tight (`render.cloudMode`, `render.cloudBudgetMs`; `?clouds=volumetric|billboard|off`).
  The `low` quality preset and software renderers use the billboards.
- **Cloud shadows** — a cloud-shadow map, rendered from the same cloud field and drifting with the
  wind, is applied inside the shared fog code, so every material (ground, buildings, trees, water,
  the aircraft) gets moving cloud shadows.
- **Shadows** — the sun's shadow map follows the aircraft (±160 m) with a smooth 3×3 filter; the
  sky environment map re-bakes in slices over several frames as altitude changes.

## 9. The systems layer (src/game/systems)

Everything added on top of the core loop is a **system**: one file in `src/game/systems/` that
default-exports `{ name, order, create(ctx) }`. `systems/index.ts` finds them automatically
(`import.meta.glob`), creates them in `order`, and calls their hooks every frame:

| Hook | When |
| --- | --- |
| `ready(camera)` | before the first frame (e.g. terrain tiles around the runway) |
| `readings(state, controls, dt)` | one system (the HUD) provides the instrument readings |
| `cameraShake(state)` | the largest value wins |
| `adjustControls(controls, state, dt)` | before the physics steps; chained in order (the weapons system sets `gunFiring` so the physics applies the gun's recoil) |
| `update(frame)` | every frame, after the camera moves, before rendering |
| `postRender(frame)` | right after the main render (extra viewports, e.g. a missile camera) |
| `onAircraftChange(def, model)` | the player picked another aircraft (a reset follows) |
| `onAction`, `onReset`, `onResize`, `stats`, `dispose` | as named |

Current systems (order): loading (0, the start-up veil), camerafx (1, speed-dependent field of
view), crash (2, the break-up director), terrain (10), water (20), airport (30), roads (40),
ships (44), cars (45), airTraffic (46), towns (50), vegetation (60), grass (61), targets (65, the
range vehicles), airTargets (66, the enemy aircraft), weapons (70), missiles (71), fx (80),
rotorWash (81, a helicopter's downwash), combatfx (85), audio (90), hud (100), weaponsHud (101), gmeter (102), menu (105). A system that
throws is isolated and logged; the rest keep running. `?no=vegetation,towns` in the URL switches
systems off (handy for profiling; `window.sim.systems()` lists the names), and each system's CPU
time appears in `window.sim.perf.systems`. [docs/ADDING_LAND_FEATURES.md](docs/ADDING_LAND_FEATURES.md)
walks through writing one.

This design means ten engineers (or agents) can add features in parallel without ever editing
the same wiring file.

## 9b. The fleet (src/fleet) — more than one aircraft

Every flyable aircraft is an `AircraftDef` in `src/fleet/index.ts`: an id (`c172rg`, `f16`, `a10`,
`b747`, `b206`, and the yacht `v50`),
names, a **full config** (the same shape as `CONFIG`, with its own `aircraft` and `weapons` sections
and optional camera overrides — the physics, cameras, instruments and weapons just receive it),
which HUD it uses (`steam` gauges or a `jet` head-up display), which engine sound (`piston`, `jet`
or `turbofan`), and a `createModel()` factory returning an `AircraftModelHandle` (`root`,
`setVisualState`, optional panel drawer, landing light, `hudCombiner` for jets, and
`getBreakupParts()` / `restoreBreakupParts()` for the crash). The player picks one from the
dropdown at the top right (or `?aircraft=a10`); `app.ts` swaps the model and the config and
restarts on the runway, and every system hears `onAircraftChange(def, model)`.

| Id | Aircraft | HUD | Sound | Weapons |
| --- | --- | --- | --- | --- |
| `c172rg` | Cessna 172RG Cutlass | steam | piston | none |
| `f16` | F-16C Fighting Falcon | jet | jet | M61A1, 2 × AGM-65, 2 × AIM-9 (`F16_WEAPONS`) |
| `a10` | A-10C Thunderbolt II | jet | turbofan | GAU-8/A, 4 × AGM-65, 2 × AIM-9 (`A10_WEAPONS`) |
| `b747` | Boeing 747-400 (flown light, ~220 t) | steam | turbofan | none |
| `b206` | Bell 206B-3 JetRanger III (helicopter, `rotorcraft` config) | steam (dual tach, torquemeter) | turboshaft | none |
| `v50` | Princess V50 motor yacht (`kind: 'vessel'`, `watercraft` config) | marine (helm display) | marineDiesel | none |

A **vessel** is a fleet entry too (`kind: 'vessel'`, a `watercraft` config section, the model under
`src/vessels/<name>/`): the picker lists it under "Vessels", it starts at its berth instead of a
runway, and [docs/ADDING_A_VESSEL.md](docs/ADDING_A_VESSEL.md) walks through adding one (a
runabout, a ferry, a cruise ship, a warship).

**To add an aircraft:** (1) add its section to `src/config.ts` with the same shape as
`CONFIG.aircraft` — geometry first, because the physics contact points and the 3D model share it;
(2) build its model under `src/aircraft/<name>/` implementing `AircraftModelHandle`; (3) add one
entry to `FLEET`. Tests in `tests/fleet/` check every entry spawns resting on its gear, and
`tests/world/airport/crossing.test.ts` puts every aircraft on every runway end. The step-by-step
version, with a worked example, is [docs/ADDING_AN_AIRCRAFT.md](docs/ADDING_AN_AIRCRAFT.md).

## 9c. Combat (src/combat) — guns, missiles, tanks and enemy aircraft

The A-10C's and the F-16's weapons plug into the same systems layer. Everything talks through one
**combat world** per scene (`combatWorld(scene)`, `src/combat/world.ts`, plain data + pure maths):

- **Targets** — every target is a `GroundTarget` with a hull box, real sizes per class from
  `CONFIG.combat.targets`, health, alive / destroyed. Ground vehicles (`GroundKind`: T-72B tank,
  BMP-2, BTR-80, Ural-4320 truck, ZSU-23-4 Shilka) stand on the ground (`position`,
  `headingDeg`). Aircraft (`AirKind`: MiG-29 `fighter`, Su-25 `attack`, Mi-24 `helo`; classes with
  `air: true`) have a box centred on `position` with a full `orientation`; `world.isAir(t)`,
  `centreOf(t)` and `toBody(t, d)` treat both alike.
- **Hits** — `raycast(from, to)` finds the first hull a round's flight segment crosses and which
  face it struck; `applyHit` applies damage through the **armour by aspect** table
  (`src/combat/damage.ts`: a 30 mm round barely scratches a T-72's front but goes through the top
  and rear); `applyBlast` damages everything near an explosion, falling off with distance.
- **Events** — `on(listener)`: gunStart / gunStop, impact, hit, destroyed, missileLaunch,
  detonation, lock / lockLost, reload. The effects, sound and HUD react to these; nobody calls
  anybody else directly.
- **Status** — `world.status` is what the HUD shows: rounds, barrel spin, CCIP (where the gun's
  rounds would land), missiles left per rail, lock state and range.

Who does what:

| System | Job |
| --- | --- |
| `weapons` | the gun: barrels spin up, rounds fly with gravity and drag (`ballistics.ts`), hit targets and ground, recoil via `adjustControls` → `Controls.gunFiring` → the physics |
| `missiles` | the missiles, **arcade model**: T picks the target nearest the nose (a vehicle or an aircraft), LOCK after a moment, Z fires an AGM-65 Maverick at a vehicle or an AIM-9 Sidewinder at an aircraft, and the missile flies a scripted curve to it (`missile.ts`, `targeting.ts`) — deliberately not a guidance simulation |
| `targets` | plans the range north of the airport in a worker (`src/combat/targets/plan.ts`: a convoy on the farm lane, a tank platoon behind berms, Shilkas in revetments, a logistics park), drives the convoy (it halts, scatters and regroups when attacked), draws the vehicles instanced with three levels of detail, contact shadows and dust, and their wrecks |
| `airTargets` | the enemy aircraft (`src/combat/air/`): MiG-29 pairs on patrols around the range, a Su-25 pair making attack passes, a Mi-24 pair circling low; banked kinematic flight with terrain following, evasive breaks and flares when locked or shot at, shoot-downs (falling in flames, losing parts, a burning wreck) and a replacement a minute later. They never shoot back |
| `combatfx` | impact dust and sparks, explosions, the GAU-8's sound |
| `weaponsHud` | gun cross, CCIP pipper, lock box, ammo, kills, the arrow to the range |

Each aircraft's weapons are part of its config (`config.weapons`, a `WeaponsConfig` with `gun`,
`missiles` and `airMissiles`: `A10_WEAPONS`, `F16_WEAPONS`; the Cessna and the 747 carry
nothing). Keys: hold **Q** / Enter to fire the gun, **T** to pick a target, **Z** to fire a
missile. `?spawn=range` starts you near the targets; `window.sim.combat` shows it all, and
`window.sim.combatDebug` / `window.sim.airTargets` help QA. Adding target classes is covered in
[docs/ADDING_VEHICLES_AND_TARGETS.md](docs/ADDING_VEHICLES_AND_TARGETS.md).

**Naval guns** (`src/combat/naval*.ts`; systems `navalGuns`, `navalHud`, `navalRange`, `navalAudio`):
any vehicle whose `config.weapons.naval` is set (the USS Iowa) gets turrets that train and elevate
at their real rates toward a ballistic fire-control solution for the point under the mouse (or a
locked target), respect their training arcs, and fire rippled salvos on Q from the guns that are
loaded and on target. Shells are unguided (drag, flight times up to ~90 s); water columns, muzzle
blast and a pressure ring are effect meshes. `WeaponsStatus.turrets` drives the ship's model
(`AircraftVisualState.turrets`). The gunnery range (`CONFIG.combat.gunnery`) floats rafts, hulked
freighters and a towed sled as combat targets (`SeaKind`) — the jets' guns and Mavericks hit them too.

## 10. The aircraft on screen (src/aircraft)

A procedural Cessna 172RG built entirely in code: a lofted fuselage (cross-sections joined into a
smooth skin), a NACA 2412 wing with the constant-chord inner panel and tapered outer panel, struts,
the swept fin with its dorsal fillet, retractable gear that swings into the belly, a two-blade
propeller that blurs into a faint disc at speed, and separate pivoted ailerons, flaps, elevator,
trim tab and rudder. The **retractable gear** follows the real 172RG: the doors open, the main
legs swing aft about tilted hinge axes so the wheels tuck almost flush into open belly wells (real
holes in the skin with recessed liners), the nose leg folds aft on a drag brace, then the doors
close; strut compression and nosewheel steering animate. After a crash the model shows a **wreck**
(bent prop, folded wing, collapsed gear, soot spreading) until reset. The paint (white with a navy-and-gold stripe, registration **N172JT**) is drawn onto
canvas textures. Nav lights, strobes, beacon and a landing light. The cockpit has the instrument
panel — a live canvas texture drawn by the same gauge code as the HUD — yokes that move with the
controls, seats, the door panels, the headliner and slim windshield posts. **The wheels are
exactly where the physics puts them**: both read `aircraft.geometry` from the config, and a test
checks they agree within 2 cm.

The jets follow the same contract in their own folders. `src/aircraft/f16/` builds the F-16C
(blended body, all-moving stabilators, flaperons, speed brake, afterburner nozzle and plume,
wingtip Sidewinders and Mavericks on their rails, gun port) with its cockpit and HUD combiner
glass. `src/aircraft/a10/` builds the A-10C (straight wing, twin fins, podded TF34s, the GAU-8's
seven barrels that spin, decelerons, stores) with a detailed cockpit: three-piece windscreen,
glareshield, armament panel, live instruments and MFCD pages, stick and throttles, ACES II seat.
`src/aircraft/b747/` is the Boeing 747-400. `src/aircraft/b206/` is the Bell 206 JetRanger
helicopter: its main rotor spins at the physics' rotor rpm (blurring into a disc) and tilts with the
tip-path plane, the blades feather with the collective, the tail rotor spins at the gear ratio, and
the cockpit (flown from the right seat) has the cyclic, collective and pedals moving with the
controls the rotor actually sees. Each jet's anchor tests hold the model to its
geometry within 3 cm, and the gun muzzle and missile stations to `config.weapons`.

## 11. Instruments, HUD, audio and effects

- **Instruments (`src/ui/instruments.ts`, pure)** — readings in display units with real-instrument
  behaviour (the VSI lags, needles are smoothed), plus the stall warning and gear lights. A
  helicopter gets `readings.rotor` instead of a stall warning: NR and N2 (they split on the dual
  tach when the engine quits and the rotor autorotates), N1, torque, collective, the stability
  assist, and the LOW ROTOR RPM / OVERTORQUE / VORTEX RING / RETREATING BLADE STALL annunciators.
- **Gear warning (`src/ui/gearWarning.ts`, pure)** — like the real 172RG: gear not down and locked
  in flight with the power back or flaps ≥ 20° → intermittent horn + flashing GEAR; handle up on
  the ground → "GEAR — SQUAT SWITCH" caution; gear-speed cautions.
- **Loading veil (`src/ui/veil.ts`)** — title, a Cessna silhouette and progress while the world
  streams in; dismissed by the first key or click (which also unlocks audio) — `?veil=0` skips it.
- **Gauges (`gauges.ts`)** — the six-pack (airspeed, attitude, altimeter, turn coordinator,
  heading, VSI), tachometer and compact system displays, drawn on canvas; reused for the 3D panel.
- **HUD (`hud.ts`)** — gauge clusters in the bottom corners, a compass tape at the top, a systems
  strip (throttle, flaps, gear lights, trim, brakes, engine), messages (STALL, CRASHED — reason,
  landing rating, PAUSED, confirmations for mute/light/time of day) and the help screen (H). It
  scales for 1024–1440+ px wide (simplified gauge faces below ~112 px) and keeps the middle of the
  screen clear.
- **Audio (`src/audio`)** — synthesised with Web Audio, one engine *voice* per aircraft
  (`AircraftDef.sound`, swapped with a fade on `onAircraftChange`): the Cessna's Lycoming O-360 +
  prop (firing frequency from RPM, uneven cylinders, prop buzz, exhaust), the F-16's F110
  turbofan (turbine whine at the HP blade-pass rate from N2 %, fan buzz-saw, jet roar, afterburner
  rumble + crackle + light-off whoomph, cockpit intake howl and ECS, hydraulic whine for gear and
  speed brake, directivity, distance and Doppler), the high-bypass TF34 turbofans (the A-10,
  also used for the 747) and the JetRanger's turboshaft (`turboshaft.ts`: main-rotor beat at the
  blade-passage rate from NR, blade slap that sharpens with thrust, flares, tight turns, the vortex
  ring state and blade stall, the 85 Hz tail-rotor buzz, the Allison 250's compressor whine from N1,
  start-up and spool-down, gearbox whine, and the steady low-rotor-RPM horn). Combat sound: the GAU-8's "BRRRT" heard late from outside at the speed
  of sound, impacts and explosions. Audio is suspended while the tab is hidden. Also wind, stall and gear horns, tyres, motors,
  and a layered crash (boom, crunch, metal tearing, debris, scraping, fireball, secondary
  explosions — randomised, or driven by the crash effects' `sim:explosion` / `sim:impact` window
  events — and a fire that burns down; reset silences it). Master → glue compressor → limiter →
  soft clipper, so nothing clips. Starts on the first key press or click (browser rule).
  `runAudioSelfTest()` renders and measures every sound in the page (levels, pitch, mix checks);
  `node scripts/audio-check.mjs <url>` runs it in Chrome for Testing and meters the live output.
- **Effects (`src/fx`)** — pooled GPU particles for the crash fireball (blackbody colours), a
  smoke column that drifts with the wind, burning debris and embers, and tyre smoke/dust/spray on
  touchdown; sprites that would cover too much of the screen fade out. A helicopter's **rotor
  wash** (`rotorWash.ts`, pure core + the `rotorWash` system) throws up dust, grass flecks, snow or
  spray where its wake meets the surface (strength from thrust × induced velocity, fading with
  height and blown back with speed), with a ripple ring on water.

## 13. Testing

`npm test` runs everything (Vitest, a few minutes with a GPU). Five layers — see `docs/TESTING.md`:

1. **Unit tests** mirror `src/` (e.g. `tests/physics/lift.test.ts`, `tests/camera/…`).
2. **Fuzz / property tests** (`tests/fuzz`, and inside module folders) with **fast-check**:
   thousands of random control sequences, attitudes, time steps and inputs — the physics never
   produces NaN, the controls stay in range, crashes stay final, cameras never go underground.
   Failures print a seed to replay (`FC_SEED`, `FC_PATH`).
3. **Functional tests** (`tests/functional`) — a scripted pilot flies whole missions against the
   real physics: take-off and climb, turns, stall and recovery, flying into a hill, landing, a
   gear-up landing, ditching, and a keyboard take-off through the real input path.
4. **End-to-end tests** (`*.e2e.test.ts`) — start Vite and a headless **Chrome for Testing**, load
   the real game, and drive it with the keyboard while reading `window.sim`: no console errors,
   throttle, cameras, pause, resets, gear/flaps, resizing, the menu and weapons HUD, and the
   production build under the GitHub Pages sub-path (no leaks, resizes, a hidden tab).
5. **Repository tests** (`tests/repo`) — open-source readiness: the licence, package metadata, CI,
   no personal paths or secrets, a README that lists every key binding and every aircraft, and
   docs whose links, paths, `CONFIG` paths and code names all exist.

Development is test-first: write the test, watch it fail, write the code, watch it pass.
`npx tsc --noEmit -p .` must also be clean.

## 14. Visual QA tools

- `scripts/shot.mjs` — headless screenshot of any URL (the game or a `preview/*.html` page) on the
  real GPU, printing console errors and failed requests.
- `scripts/qa-pilot.js` — injected into the page, it flies the sim **only through keyboard
  events** (like a person), reading `window.sim`, with a profile per aircraft: `takeoff()`,
  `climbTo()`, `turn()`, `gTurn()`, `dash()`, `stallAndRecover()`, `flyInto()`,
  `approachAndLand()`, `circuit()`, `rtbAndLand()`, and for combat `flyToRange()`,
  `pickTarget()`, `gunRun()`, `mavShot()`.
- `preview/*.html` — each part of the world on its own (terrain, atmosphere, aircraft, HUD…).
- **Never automate the owner's Google Chrome** — all automation uses the separate *Google Chrome
  for Testing* app (see RECORD.md).

## 15. Performance approach

Target: 60 fps at 1440×900 on an Apple M2 Max. Techniques: instancing (trees, buildings, cars,
lights, clouds), merged static geometry, quadtree terrain with worker-built tiles, distance LOD and
impostors for trees, frustum and distance culling, object pools (particles, tree chunks), no
per-frame allocations in hot paths, a capped pixel ratio with dynamic resolution, and per-system
CPU timings to find what's slow. The measured flight in RECORD.md averaged 59.9 fps.

## 16. How the project was built

Test-first, by an AI orchestrator running waves of up to ten Opus sub-agents in parallel, each in
its own git worktree on file-disjoint modules, merged back to `main` after each wave. `PLAN.md`
holds the contracts and rules; `RECORD.md` logs every wave, decision and bug with its cause.
