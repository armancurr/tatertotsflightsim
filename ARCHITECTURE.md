# Flight Simulator Architecture

This document explains how the Flight Simulator is built, in plain English. It is written for a
developer (or an AI agent) who has never seen the code. Read `ELEVATOR_PITCH.md` first for *what*
the project is; this file is *how* it works. `REPO_MAP.md` lists every file; `RESUME.md` says where
the work stopped.

---

## 1. The big picture

The simulator is a single web page (`index.html`) that loads one TypeScript entry file
(`src/main.ts`). There is no server logic — Vite serves the files during development, and the
build is a folder of static files. Everything — terrain, trees, buildings, sky, clouds, the
aircraft, textures, sounds — is **generated by code** at start-up or on the fly. Nothing is
downloaded at runtime, so there is nothing that can fail to load.

The code is split into two kinds of modules:

| Kind | What it means | Examples |
| --- | --- | --- |
| **Pure simulation** | Plain TypeScript maths. No three.js, no DOM, no clock. Same input → same output, every time. This is what the tests hammer. | `src/physics`, `src/input/controlSystem.ts`, `src/camera/cameraRig.ts`, `src/game/loop.ts`, `src/ui/instruments.ts`, `src/world/heightfield.ts`, `src/world/layout.ts` |
| **Presentation** | Draws or plays what the simulation says. Uses three.js (WebGL2), the DOM, Web Audio. Never changes the simulation state. | `src/render`, `src/aircraft`, `src/world/terrain`, `src/ui/hud.ts`, `src/audio`, `src/fx` |

This split is the single most important design rule: **the renderer only draws what the physics
says.** It is why the flight model can be tested to the decimal place without a browser.

```
 keyboard / mouse / gamepad
          │
          ▼
  input (pure) ── smoothed Controls ──▶ physics.step()  ×120 per second (fixed step)
                                              │
                                              ▼
                                        AircraftState ──▶ window.sim (for tools & tests)
                                              │
                   interpolate between the last two physics states (smooth at any frame rate)
                                              │
        ┌──────────────┬──────────────┬───────┴───────┬───────────────┬───────────────┐
        ▼              ▼              ▼               ▼               ▼               ▼
   aircraft model   camera rig    instruments      sky & sun      world systems     audio
   (surfaces, gear, (4 views,     (needles, VSI    (fog, clouds,  (terrain, water,  (engine,
    prop, lights)    transitions)   lag, warnings)  shadows)       trees, towns…)    wind, horn)
        └──────────────┴──────────────┴───────────────┴───────────────┴───────────────┘
                                              │
                                              ▼
                                   renderer.render(scene, camera)
```

## 2. Coordinates and units (read before touching any maths)

- **World:** metres. `+X` = east, `+Y` = up, `+Z` = **south** (so north is `−Z`). `y` is height
  above mean sea level. This is the three.js convention, so the renderer needs no conversion.
- **Heading:** degrees clockwise from north (0 = north/−Z, 90 = east/+X).
- **Aircraft body:** the same as a three.js object: `+X` right wing, `+Y` up, **`−Z` the nose**.
  The origin is the centre of gravity. The physics' orientation quaternion can be copied straight
  onto the 3D model.
- **Aircraft-convention quantities** (angle of attack α, sideslip β, roll/pitch/yaw rates p/q/r,
  roll/pitch/yaw moments L/M/N) are converted **only** through the helpers in
  `src/physics/frames.ts`. Never re-derive signs by hand — `tests/physics/frames.test.ts` pins them.
- Units are SI inside the code. Knots, feet and feet-per-minute appear only at the edges (HUD,
  `window.sim`, config keys whose names end in `Kt`, `Ft`, `Fpm`, `Deg`).

`src/types.ts` holds these conventions in its header and defines the shared shapes
(`AircraftState`, `Controls`, `Environment`, `InstrumentReadings`, `SimSnapshot`).

## 3. One config file

`src/config.ts` holds **every tunable number**: the aircraft (mass, wing area, lift/drag
coefficients, stall angle, stability derivatives, engine power, gear geometry, landing limits),
controls (key bindings, smoothing rates), cameras (distances, FOVs, transition time), the world
(seed, airport, terrain LOD, trees, towns, water, traffic), the atmosphere (sun presets, fog,
exposure, clouds, shadows), rendering quality, audio and HUD. Each top-level section is owned by
one module. Balancing the sim is one edit; tests can clone the config (`cloneConfig()`) and change
values without touching the real one.

## 4. The frame (src/game/app.ts)

`startApp()` builds everything once, then runs this every animation frame:

1. **Input** — `input.frame()` collects held keys, key presses, mouse drags/wheel and gamepad
   axes; `updateControls()` turns them into smooth control positions (throttle, yoke, rudder, trim,
   flaps notch, gear handle, brakes, engine switch) plus discrete **actions** (reset, pause,
   camera change, help, mute, time of day).
2. **Physics at a fixed 120 Hz** — `FixedStepLoop.advance()` runs `step(state, controls, 1/120,
   env)` as many times as real time requires (capped so a slow frame can't spiral). The render
   frame rate never changes the physics.
3. **Interpolation** — the aircraft is drawn between the last two physics states, so motion is
   smooth at 60, 90 or 144 Hz.
4. **Instruments & aircraft animation** — readings (with real-instrument lag) drive the HUD and the
   cockpit panel; control positions drive the elevator, ailerons, rudder, flaps, gear and prop.
5. **Camera** — the camera rig computes the pose for the current view and blends between views.
6. **World** — the atmosphere updates (sun shadows follow the aircraft, clouds, fog), then every
   **system** updates (terrain tiles, trees, towns, water, traffic, effects, audio, HUD).
7. **Render**, then update `window.sim` and the FPS meter.

While paused, the world keeps rendering (so it streams in), but the physics and the control
toggles freeze.

## 5. The physics (src/physics)

A six-degrees-of-freedom rigid-body model of the Cessna 172RG, deterministic and pure.
`step(state, controls, dt, env?)` returns a **new** state (it never mutates its input).

- **Air data:** the aircraft's velocity relative to the air (minus wind) is rotated into the body
  frame to get airspeed, angle of attack and sideslip; air density follows the standard atmosphere.
- **Aerodynamics (`aero.ts`):** the lift coefficient rises with angle of attack and flaps, rounds
  off at the stall angle (≈15.5° clean) and collapses toward flat-plate behaviour past it; drag is
  parasite + gear + flaps + induced (lift²) + sideslip, rising to flat-plate drag past the stall.
  Pitch, roll and yaw moments use published C172 stability derivatives (damping, dihedral effect,
  weathercock stability, adverse yaw). The propeller slipstream adds airflow over the tail (so
  elevator and rudder work at full power on the ground). Past the stall the wing loses its roll
  damping — an uncoordinated stall drops a wing. **Ground effect:** near the runway the wing makes a
  little more lift and less induced drag (McCormick's formula).
- **Engine (`engine.ts`):** power follows the throttle with a lag, falls with air density; thrust
  comes from power and airspeed (strong at low speed, falling as speed rises); a windmilling prop
  adds drag. The engine can be switched off, cranks for ~1.4 s to restart, and fails in a crash.
- **Ground (`ground.ts`):** three spring-damper struts (nose and two mains) at the exact wheel
  positions of the 3D model, rolling friction by surface (runway, grass, dirt…), brakes, sideways
  tyre grip, nosewheel steering from the rudder. Structural points (prop tip, wingtips, tail,
  belly…) that touch the ground mean a crash; a gentle tail scrape only skids.
- **Systems:** flaps move at the electric motor's rate; the gear takes 5 s and only retracts after
  1.5 s of continuous flight (squat-switch interlock).
- **Flight phases:** `ground` → `airborne` → (touchdown) `landed` or `crashed`; a `stalled` flag
  while airborne. Touchdowns are rated by vertical speed (butter < 120 fpm, smooth, firm, hard; over
  900 fpm the gear collapses). Crashes record a reason, the speed and position; the engine fails
  and the state freezes until reset. Over-G (6.5 g) or diving past 1.3 × Vne breaks the airframe.
- **Trim solver (`trim.ts`):** finds the throttle, pitch and trim for a steady flight condition —
  used for the final-approach reset (Shift+R) and teleports.

Calibration results against the pilot's handbook are in the comment block at the top of
`src/physics/aircraft.ts`.

## 6. Controls, cameras and the loop

- **Controls (`src/input`)** — pure `updateControls(state, inputFrame, dt)`. Keys move the yoke
  toward full deflection at a set rate and back to centre when released (the elevator eases off
  slowly, like a pilot relaxing back pressure); throttle and trim stay where you leave them; flaps
  step through 0/10/20/30°; G toggles the gear handle. Mouse-yoke (Y) and gamepads are supported.
  The DOM adapters stop bound keys scrolling the page and clear held keys when the window loses
  focus (no stuck keys).
- **Cameras (`src/camera`)** — pure `updateCameraRig()`: **cockpit** (pilot's eye, head look with
  the mouse), **chase** (spring-damped behind the aircraft), **external** (a fly-by spotter that
  re-positions ahead of the aircraft), **orbit** (drag to rotate, wheel to zoom, slow auto-spin).
  Switching views blends position, rotation and field of view over ~0.9 s. Cameras never go below
  the ground. Camera shake comes from the ground roll, stall buffet and crashes.
- **Loop (`src/game/loop.ts`, `fps.ts`, `interpolate.ts`)** — the fixed-step accumulator, the FPS
  meter (1-second fps, session average, worst second, 1 % low, long frames), and pose interpolation.

## 7. The world

### 7.1 Geography as data (pure)
- `layout.ts` — the whole map as plain data from the config and a seed: the airport (runway 36/18,
  taxiways, apron, building spots), the coastline and bay with islands, two lakes, the river from
  the mountains to the sea, 26 towns (a coastal city, a town, villages, hamlets), and the road
  network.
- `heightfield.ts` — `terrainHeight(x, z)`: rolling farmland, a mountain range to the north,
  carved river and lake beds, beaches into the sea, and the airport plateau **exactly** flat at
  30 m. `landcover.ts` decides what covers the ground (forest, field, grass, rock, snow, sand,
  town, water) and `treeDensity()`; `fields.ts` is the farm-field pattern, shared bit-for-bit with
  the terrain shader.
- `environment.ts` — the physics' view of the world (`Environment`): ground height and slope,
  surface type, water level, and **obstacles** (trees, buildings, the tower register themselves),
  built from the same functions the renderer draws — **what you see is what you hit**.
- `runway.ts` — runway coordinates shared by the physics (spawn, landing rating) and the world.

### 7.2 Drawing the world
Heavy generation (terrain tiles, tree chunks, building placement, road meshes, detail textures,
water depth maps) runs in **Web Workers**; the main thread only uploads results a few per frame, so
flying fast never hitches.

- **Terrain (`src/world/terrain`)** — a quadtree of tiles around the camera: small detailed tiles
  near, big coarse ones far, out to ~60 km, with skirts to hide cracks, pooled geometry and correct
  bounding spheres for culling. Heights **and colours** morph between detail levels so nothing
  pops. The shader (built on three.js's standard material, so lighting, shadows and fog work)
  paints the ground from the landcover: realistic farmland (ten crop types, drill rows, tractor
  tramlines, ploughed furrows, hedges and farm tracks, soil patterns), forest floors, town lots
  with lawns and driveways, rock with warped strata and scree, snow that lingers in gullies,
  beaches. Close up, eight **procedurally generated detail textures** (grass, crop, soil, gravel,
  rock, sand, snow, straw) are blended by height, with random per-tile offsets so nothing repeats.
- **Water (`src/world/water`)** — twelve wind-driven wave trains (the same maths is exposed as
  `waterSurfaceAt()` for boats), an FFT-generated ripple texture for sparkle and the sun's glitter
  path, a depth/shore map baked in a worker around the camera (turquoise shallows over sand, dark
  deep water, surf lines and foam), a continuous flowing river ribbon that coarse terrain can never
  hide, and calm mirror-like lakes on still mornings.
- **Airport (`src/world/airport`)** — pavement with aggregate, rubber marks, cracks and patches,
  worn FAA paint, the control tower, five hangars (one open with an aircraft inside), the FBO with
  its sign, fuel station, windsock, fence, 15 parked Cessnas and Pipers, cars, signs, and ~290
  lights in one draw call: edge, threshold, taxiway, approach lights with the sequenced "rabbit",
  the rotating beacon and two working **PAPIs**. Buildings are obstacles.
- **Roads (`src/world/roads`)** — a junction network (2,000+ nodes) turned into road surfaces with
  sidewalks, shoulders and soft verges, US-style markings (double yellow, dashed lines, crosswalks,
  stop bars), dirt farm tracks, bridges with decks, piers and guard rails, and ~4,000 street lights
  that glow at dusk. A small depth pull keeps roads from sinking into coarse terrain.
- **Towns (`src/world/towns`)** — ~10,600 buildings: houses with gable/hip roofs, chimneys and
  dormers, terraces, apartment blocks, glass towers, churches, industrial sheds, farmsteads with
  barns and silos. One small mesh per building type is stretched per instance in the vertex shader;
  a facade shader draws windows, doors, shopfronts and roof materials; windows light up at dusk.
  Placement runs in a worker; far towns collapse into one self-culling mesh. Rooftops are obstacles.
- **Trees (`src/world/vegetation`) and grass (`src/world/grass`)** — seven species built from leaf
  cards (spruce, pine, broadleaf, birch, poplar, willow, bush) with back-lit leaves and wind sway;
  multi-angle **impostors** (pre-rendered images) take over beyond ~210 m and fade out around
  4.5 km. Forests, clearings, hedgerows on field edges, orchards, willows along the river. Grass
  tufts and wildflowers appear near the camera when flying low. Trees are obstacles — flying into a
  forest is a crash.
- **Traffic (`src/world/traffic`)** — ship and boat routes (a marina, sailing yachts that tack,
  a ferry, a container ship, a tanker, lake boats, wakes) and air traffic (runway-36 circuits,
  crossing aircraft, a helicopter, airliners with contrails) are simulated and tested, with models
  built — **but not yet drawn** (see RESUME.md).

## 8. Sky, light and rendering (src/render)

- **Renderer (`renderer.ts`)** — WebGL2 with a **reversed float depth buffer** (no flickering
  between the 8 cm cockpit panel and a mountain 60 km away), rendering in linear HDR with 4× MSAA,
  then one output pass with a filmic tone map; resolution scales down automatically if the frame
  rate drops.
- **Atmosphere (`atmosphere.ts`)** — a physically based sky (single scattering: deep blue overhead,
  pale haze at the horizon, a real sun disc), a sun light whose colour follows its height, soft
  shadows that follow the aircraft, and a sky environment map for reflections. Four time-of-day
  presets (N key).
- **Aerial perspective (`fog.ts`)** — three.js's fog code is replaced for **every** material:
  height-based haze that is blue away from the sun and warm toward it, matched to the sky at the
  horizon, so distant hills fade like real ones. Any material with `fog: true` gets it for free.
- **Clouds** — by default a field of instanced billboard cumulus around the camera, lit from the
  sun, drifting with the wind, with a soft whiteout inside a cloud. An experimental **volumetric**
  ray-marched cloud layer (half resolution, temporal accumulation, depth-aware compositing, a
  budget controller that falls back to billboards) is built but off by default because it costs
  3–5 ms (`?clouds=volumetric&cloudbudget=0`).
- **Cloud shadows** — a cloud-shadow map, rendered from the same cloud field and drifting with the
  wind, is applied inside the shared fog code, so every material (ground, buildings, trees, water,
  the aircraft) gets moving cloud shadows.
- **Shadows** — the sun's shadow map follows the aircraft (±160 m) with a smooth 3×3 filter; the
  sky environment map re-bakes in slices over several frames as altitude changes.

## 9. The systems layer (src/game/systems)

Everything added on top of the core loop is a **system**: one file in `src/game/systems/` that
default-exports `{ name, order, create(ctx) }`. `systems/index.ts` finds them automatically
(`import.meta.glob`), creates them in `order`, and calls their hooks every frame:

| Hook | When |
| --- | --- |
| `ready(camera)` | before the first frame (e.g. terrain tiles around the runway) |
| `readings(state, controls, dt)` | one system (the HUD) provides the instrument readings |
| `cameraShake(state)` | the largest value wins |
| `update(frame)` | every frame, after the camera moves, before rendering |
| `onAction`, `onReset`, `onResize`, `stats`, `dispose` | as named |

Current systems (order): loading (0, the start-up veil), camerafx (1, speed-dependent field of
view), terrain (10), water (20), airport (30), roads (40), towns (50), vegetation (60), grass (61),
fx (80), audio (90), hud (100). (Traffic has no system file yet.) A system that throws is isolated and
logged; the rest keep running. `?no=trees,towns` in the URL switches systems off (handy for
profiling), and each system's CPU time appears in `window.sim.perf.systems`.

This design means ten engineers (or agents) can add features in parallel without ever editing
the same wiring file.

## 10. The aircraft on screen (src/aircraft)

A procedural Cessna 172RG built entirely in code: a lofted fuselage (cross-sections joined into a
smooth skin), a NACA 2412 wing with the constant-chord inner panel and tapered outer panel, struts,
the swept fin with its dorsal fillet, retractable gear that swings into the belly, a two-blade
propeller that blurs into a faint disc at speed, and separate pivoted ailerons, flaps, elevator,
trim tab and rudder. The **retractable gear** follows the real 172RG: the doors open, the main
legs swing aft about tilted hinge axes so the wheels tuck almost flush into open belly wells (real
holes in the skin with recessed liners), the nose leg folds aft on a drag brace, then the doors
close; strut compression and nosewheel steering animate. After a crash the model shows a **wreck**
(bent prop, folded wing, collapsed gear, soot spreading) until reset. The paint (white with a navy-and-gold stripe, registration **N172JT**) is drawn onto
canvas textures. Nav lights, strobes, beacon and a landing light. The cockpit has the instrument
panel — a live canvas texture drawn by the same gauge code as the HUD — yokes that move with the
controls, seats and the windshield frame. **The wheels are exactly where the physics puts them**:
both read `aircraft.geometry` from the config, and a test checks they agree within 2 cm.

## 11. Instruments, HUD, audio and effects

- **Instruments (`src/ui/instruments.ts`, pure)** — readings in display units with real-instrument
  behaviour (the VSI lags, needles are smoothed), plus the stall warning and gear lights.
- **Gear warning (`src/ui/gearWarning.ts`, pure)** — like the real 172RG: gear not down and locked
  in flight with the power back or flaps ≥ 20° → intermittent horn + flashing GEAR; handle up on
  the ground → "GEAR — SQUAT SWITCH" caution; gear-speed cautions.
- **Loading veil (`src/ui/veil.ts`)** — title, a Cessna silhouette and progress while the world
  streams in; dismissed by the first key or click (which also unlocks audio) — `?veil=0` skips it.
- **Gauges (`gauges.ts`)** — the six-pack (airspeed, attitude, altimeter, turn coordinator,
  heading, VSI), tachometer and compact system displays, drawn on canvas; reused for the 3D panel.
- **HUD (`hud.ts`)** — gauge clusters in the bottom corners, a compass tape at the top, a systems
  strip (throttle, flaps, gear lights, trim, brakes, engine), messages (STALL, CRASHED — reason,
  landing rating, PAUSED, confirmations for mute/light/time of day) and the help screen (H). It
  scales for 1024–1440+ px wide (simplified gauge faces below ~112 px) and keeps the middle of the
  screen clear.
- **Audio (`src/audio`)** — synthesised with Web Audio, one engine *voice* per aircraft
  (`AircraftDef.sound`, swapped with a fade on `onAircraftChange`): the Cessna's Lycoming O-360 +
  prop (firing frequency from RPM, uneven cylinders, prop buzz, exhaust) and the F-16's F110
  turbofan (turbine whine at the HP blade-pass rate from N2 %, fan buzz-saw, jet roar, afterburner
  rumble + crackle + light-off whoomph, cockpit intake howl and ECS, hydraulic whine for gear and
  speed brake, directivity, distance and Doppler). Also wind, stall and gear horns, tyres, motors,
  and a layered crash (boom, crunch, metal tearing, debris, scraping, fireball, secondary
  explosions — randomised, or driven by the crash effects' `sim:explosion` / `sim:impact` window
  events — and a fire that burns down; reset silences it). Master → glue compressor → limiter →
  soft clipper, so nothing clips. Starts on the first key press or click (browser rule).
  `runAudioSelfTest()` renders and measures every sound in the page (levels, pitch, mix checks);
  `node scripts/audio-check.mjs <url>` runs it in Chrome for Testing and meters the live output.
- **Effects (`src/fx`)** — pooled GPU particles for the crash fireball (blackbody colours), a
  smoke column that drifts with the wind, burning debris and embers, and tyre smoke/dust/spray on
  touchdown; sprites that would cover too much of the screen fade out.

## 12. `window.sim` — the page's state for tools

`src/game/simApi.ts` publishes a live object on the page: `airspeed` (kt), `altitude` (ft),
`heading`, `pitch`, `roll`, `throttle` (%), `gear`, `flaps`, `state`, `fps`, plus vertical
speed, AGL, angle of attack, RPM, engine, camera, paused, crash reason, last landing,
`perf` (fps stats + per-system CPU ms), `render` (draw calls, triangles), and actions:
`reset()`, `resetApproach()`, `setCamera(mode)`, `pause()`, `resume()`, `teleport({x, z, aglFt,
headingDeg, speedKt})`, `setTimeOfDay(i)`, `debug()`. Browser tests and the QA pilot read it
instead of reading pixels. URL options: `?spawn=x,z,aglFt,hdg,kt`, `&cam=`, `&tod=`, `&pause=1`,
`&no=`.

## 13. Testing

`npm test` runs everything (Vitest, ~30 s). Four layers — see `docs/TESTING.md`:

1. **Unit tests** mirror `src/` (e.g. `tests/physics/lift.test.ts`, `tests/camera/…`).
2. **Fuzz / property tests** (`tests/fuzz`, and inside module folders) with **fast-check**:
   thousands of random control sequences, attitudes, time steps and inputs — the physics never
   produces NaN, the controls stay in range, crashes stay final, cameras never go underground.
   Failures print a seed to replay (`FC_SEED`, `FC_PATH`).
3. **Functional tests** (`tests/functional`) — a scripted pilot flies whole missions against the
   real physics: take-off and climb, turns, stall and recovery, flying into a hill, landing, a
   gear-up landing, ditching, and a keyboard take-off through the real input path.
4. **End-to-end tests** (`tests/e2e`) — start Vite and a headless **Chrome for Testing**, load the
   real game, and drive it with the keyboard while reading `window.sim`: no console errors,
   throttle, cameras, pause, resets, gear/flaps, resizing.

Development is test-first: write the test, watch it fail, write the code, watch it pass.
`npx tsc --noEmit -p .` must also be clean.

## 14. Visual QA tools

- `scripts/shot.mjs` — headless screenshot of any URL (the game or a `preview/*.html` page) on the
  real GPU, printing console errors and failed requests.
- `scripts/qa-pilot.js` — injected into the page, it flies the sim **only through keyboard
  events** (like a person), reading `window.sim`: `takeoff()`, `climbTo()`, `turn()`,
  `stallAndRecover()`, `flyInto()`, `approachAndLand()`.
- `preview/*.html` — each part of the world on its own (terrain, atmosphere, aircraft, HUD…).
- **Never automate the owner's Google Chrome** — all automation uses the separate *Google Chrome
  for Testing* app (see RECORD.md).

## 15. Performance approach

Target: 60 fps at 1440×900 on an Apple M2 Max. Techniques: instancing (trees, buildings, cars,
lights, clouds), merged static geometry, quadtree terrain with worker-built tiles, distance LOD and
impostors for trees, frustum and distance culling, object pools (particles, tree chunks), no
per-frame allocations in hot paths, a capped pixel ratio with dynamic resolution, and per-system
CPU timings to find what's slow. The measured flight in RECORD.md averaged 59.9 fps.

## 16. How the project was built

Test-first, by an AI orchestrator running waves of up to ten Opus sub-agents in parallel, each in
its own git worktree on file-disjoint modules, merged back to `main` after each wave. `PLAN.md`
holds the contracts and rules; `RECORD.md` logs every wave, decision and bug with its cause.
